# e2e-shot

変更が実際の画面で期待どおり動くかを **ego-browser** で実操作して確かめ、スクリーンショットを根拠に報告する。

対象: `$ARGUMENTS`（空なら、直前の会話と `git diff` / `git status` から推定）

## 0. 依存を確かめる

```bash
bash "${CLAUDE_SKILL_DIR}/../../scripts/doctor.sh" shot
```

NG があれば、その直し方をユーザーに伝えて止まる。

## 1. 事前チェック（足りなければ質問する）

設定を読む:

```bash
python3 -I "${CLAUDE_SKILL_DIR}/../../scripts/config.py" show
```

（`python3` が落ちるなら `/usr/bin/python3`）。テスト対象のプロジェクトのディレクトリで実行する。`.claude/ego-e2e.json` をカレントから上へ探す。

次の 3 つを、**引数 → 設定 (`targets` / `preconditions`) → 会話・`git diff`** の順に探して埋める。

| 項目 | 例 |
| --- | --- |
| 対象の URL かポート | `http://localhost:3041`、`3051 番の予約画面` |
| 実行するテストケース | 「変更期限を過ぎた予約は変更ボタンが出ない」など |
| 前提条件 | ログイン済みのアカウント、必要なデータ、フラグ |

- 1 つでも埋まらなければ、**`AskUserQuestion` でまとめて聞いてから進む**。よくあるポート (3000 / 8080 など) を推測で使わない。
- 設定の `notes` にプロジェクト固有の注意があれば従う。
- 埋めた 3 つを、最初の報告で 1 行ずつ示す（ユーザーが誤りに気づけるように）。

## 2. ブラウザとサーバーの準備

1. `Skill` ツールで `ego-browser` を起動し、その手順（`ego-browser skill`）に従う。
2. 対象 URL が応答するか `curl -sI` で確かめる。同じリポジトリの checkout / worktree が複数あるときは、ポートのプロセスが今の作業ツリーのものかも確かめる（`lsof -nP -iTCP:<ポート> -sTCP:LISTEN -t` の PID について `lsof -a -p <PID> -d cwd`）。
3. 起動していなければ、**起動してよいかユーザーに確認してから**起動する。

## 3. テストケースを宣言する

変更に関わる **エッジケースを含む約 10 件** を、先に表で書く。

| ID | エッジケース | データと条件 | 期待 |
| --- | --- | --- | --- |

正常系に加え、エラー系・境界値・権限・モバイル幅を含める。期待値はコードを読んで決め、判定ロジックの場所を `file_path:line_number` で示す。

## 4. 実操作して撮る

- 実際にクリック・入力・送信する。「画面が開いた」で合格にせず、**操作の結果**（完了画面・反映された内容・エラー文言）を見て合否を決める。
- 1 ケース 1 枚を基本に、状態が変わる箇所（操作前／後／エラー）を撮る。
- コンソールエラーとネットワークエラー（API・GraphQL の失敗など）を拾う。
- スクショは作業用の一時ディレクトリ（スクラッチパッドがあればそこ）に保存し、`Read` で中身を確かめてから見せる。

## 5. 報告

- ケースごとに ✅ / ❌ と根拠のスクショ。パスは `file://` のクリック可能なリンク（`urllib.parse.quote` でエンコード）。
- 不具合は再現手順と該当箇所（`file_path:line_number`）。
- 確かめられなかったこと（データ・権限不足など）は、そのまま書く。

## 守ること

- 操作は `localhost` などローカルの環境だけ。本番・ステージングや外部 URL は、先にユーザーに確認する。
- データを変える操作、決済・メール・外部サービスへの送信が起きる操作は、実行前にユーザーに確認する。
- コードは直さない。不具合を見つけたら報告で止める。
- 本物の認証情報（ID・パスワード・トークン・個人のメールアドレス）が入った状態は撮らない。ログイン画面そのもののテストは、テスト用のダミー値で撮る。見せる前に、スクショに認証情報が映っていないか確かめる。
